## 1. Background

`SOL-AP-004` (Business Rules AP-001..AP-074) and `SOL-AP-005` (Table Design) were completed as "DRAFT — SOURCE ALIGNED" with five rules classified PENDING (AP-013, AP-022, AP-032, AP-063, AP-066) and a list of open design questions (`SOL-AP-005` §15, §23): the property/asset type values, the custodianship end-reason values, the document `relationship_type` values, the `property_id`/`asset_id` format, the holding-arrangement and location normalisation, and the Heritage cross-reference for sacred articles. `SOL-AP-005` §24 states that no SQL may be generated from undocumented assumptions. Implementing the module nevertheless requires a concrete representation for each of these. This record lists every such choice so that none is made silently.

No CONSTITUTIONAL rule (24 of them) conflicts with the implementation. The ERP and CROSS-MODULE rules are implemented as written (see §3).

## 2A. Interpretations of the lifecycle (SOL-AP-003) made by the implementation

These are not PENDING rules but gaps between the lifecycle text and an executable contract; each is the narrowest reading of the text.

1. **Transitions** are exactly the diagram of §3.2/§4.2 plus AP-LIF-002 (UNDER_MAINTENANCE → DISPOSED/RETIRED). REGISTERED → DISPOSED/RETIRED is **not** allowed (the diagram shows disposal only from ACTIVE/IN_CUSTODY); a record registered in error is archived (soft-deleted) instead. Enforced in the API and, as a backstop, by the DB trigger `nss.fn_ap_entity_guard()`.
2. **REGISTERED → ACTIVE/IN_CUSTODY** happens automatically when the first custodian is assigned (§3.3: "property enters active state when custody is assigned"), and cannot be done manually without a custodian (AP-LIF-001). A manual `transition` to ACTIVE remains valid when a custodian exists.
3. **Custodianship ASSIGNED → ACTIVE** (AP-042) are two writes in one transaction; the row ends the request ACTIVE. Future-dated custody is not supported (`effective_from` may not be in the future); an ASSIGNED row is therefore never observable.
4. **Disposal / retirement** is *recorded* here, not approved (AP-025/045/073): the optional `remarks` of the transition (intended for the Governance decision reference) goes to the audit trail (`system_event_log.detail`); there is deliberately no approval table and no financial field. Owner decision 2026-11-03 (§2F): the terminal transition also ENDs the active custodianship in the same transaction, and the record keeps showing its LAST custodian; further custody assignment/transfer is refused (AP-046/047).
5. **Archive** (`DELETE`) is a soft delete only for a record that is REGISTERED (registered in error) or already DISPOSED/RETIRED; a live record must first have its disposal recorded. Custodianship rows have **no** delete endpoint (AP-018).
6. **Acquisition "how"** (AP-023: "record when and how a property or asset was acquired"): the approved table design stored only `acquired_at`, a gap in `SOL-AP-005` itself, flagged here rather than papered over. **Resolved 2026-11-03 by owner decision (§2E):** an optional master-data `ACQUISITION_METHOD` column on both tables. The approval reference still lives with Governance (AP-025).

## 2B. Authorization decisions (AP-074)

1. **Permissions** `ASSET_VIEW` / `ASSET_MANAGE` (module code `ASSET`), added by the idempotent patch `database/seed/00_bootstrap/05_assets_property_permissions_patch.sql` (permission_master 28 → 30, role_permission 166 → 178: 12 grants). The 4 grants withdrawn by the owner on 2026-11-02 (item 2) are soft-deleted (`is_active = FALSE`) on databases that already ran the original 16-row version of the patch, by `database/seed/00_bootstrap/06_assets_property_permissions_revoke_patch.sql`; on a fresh build they are simply never inserted. Rows are deactivated, never deleted (`role_permission` is soft-delete only: `chk_role_permission_soft_delete`, no DELETE grant, "history is never hard-deleted"); both permission loaders in `rbac_service.py` already filter `rp.is_active = TRUE`, so the withdrawal is immediate.
2. **Grants** (owner-directed 2026-11-02, amending the original draft that followed the Correspondence footprint): `ASSET_VIEW` + `ASSET_MANAGE` for `NSS_ERP_ADMIN`, `NSS_ERP_KENDRA_ADMIN`, `NSS_ERP_SAKHA_ADMIN` (AP-020: Sakha office-bearers are custodians) and `NSS_ERP_PATHA_CHAKRA_ADMIN`; **`ASSET_VIEW` only** (view-only) for `NSS_ERP_ANCHALIKA_ADMIN` and `NSS_ERP_ZILLA_ADMIN` (they see the physical organizations beneath them through the ordinary admin-scope rule but cannot change anything) and for `NSS_ERP_AUDITOR` and `NSS_ERP_REPORT_VIEWER`. **No `ASSET_*` at all** for `NSS_ERP_KENDRA_MAHILA_SANGHA_ADMIN` (owner decision: no Mahila Sangha can be a custodian, so the grants reached nothing). **Not granted:** `NSS_ERP_ATTENDANCE_MARKER` (single-purpose role) and `NSS_ERP_ADVISORY_BOARD_ADMIN` (the source gives the Advisory Board no property provision; least privilege — an owner decision). Withdrawn from the original 16: Mahila VIEW + MANAGE, Anchalika MANAGE, Zilla MANAGE.
3. **Scope** is evaluated on the **current custodian organization** of the record. A record with no custodian has no organizational anchor and is visible/manageable only by the global authority (`NSS_ERP_ADMIN` / NSS-WIDE / KENDRA scope), the same convention as a person with no Sangha Sevi. A scope-bounded admin must therefore name an in-scope custodian when registering. A custody **transfer** needs scope over both the releasing and the receiving organization, so a scope-bounded admin can neither hand a record to an unrelated unit nor take one from another; cross-scope moves (including dissolution vesting into Kendra) are done by an administrator whose scope covers both. After a transfer the record leaves the former custodian's scope; its custody history stays readable to whoever can read the record today.
4. **No member or public exposure.** Every endpoint requires a login and an `ASSET_*` permission.

## 2C. Organization-type decision (owner-directed, 2026-11-02)

1. **Custodians are physical organizations.** NSS has two kinds of organization: CONCEPTUAL (Zilla Sangha, Anchalika Sangha — administrative groupings, no premises) and PHYSICAL (Sakha, Patha Chakra, Kendra, Nilachala Kutira, Smruti Mandira). Per the owner ("all the assets will come to Sakhas"), property and assets are HELD only by physical organizations. Custodian-eligible types: `SAKHA_SANGHA`, `SAKHA_ASANA` (a Sakha Asana is a Sakha for all purposes, GDR-008), `PATHA_CHAKRA`, `KENDRA`, `NILACHALA_KUTIRA`, `SMRUTI_MANDIRA`. Not custodians: Anchalika/Zilla Sangha, wing organizations (Kumari, Sevak, local Mahila Sangha, Paribarik Asana/Sangha), the central Mahila Sangha and the Advisory Board organization (their things belong to their Sakha / the Kendra).
   - **Enforcement.** API: 422 on create-with-custodian, first-custodian assignment and transfer, naming the organization's type and saying to assign to the Sakha/physical organization instead. DB: trigger `trg_custodianship_custodian_guard` (BEFORE INSERT OR UPDATE OF `custodian_organization_pk` on `nss.custodianship`) calls `nss.fn_is_asset_custodian_org_type()`; it never scans existing rows, so a custodianship stored before the rule is left as is (`03_validate` WARNs). UI: every custodian picker offers only eligible types.
   - **One definition per layer:** Python `ASSET_CUSTODIAN_ORG_TYPES` (`api/helpers.py`, built from `SAKHA_LIKE_ORG_TYPES`), SQL `nss.fn_is_asset_custodian_org_type()` (`ddl/11_assets_property/09_asset_custodian_org_type_function.sql`), JS `NSS.ASSET_CUSTODIAN_ORG_TYPES` (`nss-config.js`); kept in step by `tests/api/test_asset_custodian_parity.py`. A master-data attribute ("holds assets") per organization type would be the Configuration-Over-Hardcoding alternative; it is not built (no per-type attribute mechanism exists for organization types), so the three-layer constant stands — open question 6.
   - **Reach.** Admins of a conceptual organization still see and manage the records of the physical organizations beneath them through the ordinary admin-scope subtree rule; list endpoints accept `include_sub_organizations=true` with a custodian filter (that organization AND its subtree, still intersected with the caller's scope). Consequence for §2B.2 (owner decisions 2026-11-02): the `NSS_ERP_KENDRA_MAHILA_SANGHA_ADMIN` scope covers only Mahila Sangha organizations, none eligible, so that role no longer holds any `ASSET_*` grant; Anchalika / Zilla admins reach the physical organizations beneath them read-only.
   - **Interaction with the AP rules.** No conflict with AP-014 (Kendra and Sakhas remain custodians), AP-020 (Sakha custodianship) or AP-015..AP-019; the restriction refines which organization units may be named. Amendment notes recorded in `04_assets_property_business_rules.md` (AP-015, AP-020) and `05_assets_property_table_design.md` §9.

## 2D. "Belongs to" attribution (owner-directed, 2026-11-02)

1. **Optional attribution, distinct from the custodian.** A property or asset may carry a nullable `belongs_to_organization_pk` (FK to `nss.organization`, on both `nss.property` and `nss.asset`): the organization it *belongs to* when that differs from the physical custodian. Example: an asset that belongs to the Mahila Sangha but is held under the supervision of the Kendra Sangha — custodian = Kendra, belongs to = Mahila Sangha. This gives the organizations that cannot be custodians (§2C: Mahila Sangha incl. the central one, Kumari, Sevak, Paribarik, and also Zilla/Anchalika Sangha) a place to be recorded without weakening the physical-custodian rule.
2. **Informational only.** It has **no** effect on authorization, admin scope (scope is still evaluated solely on the current custodian, §2B.3), the custodian-type rule, custodianship or the lifecycle. Setting it never requires scope over the named organization (attribution is not authority), and being named in it grants the named organization's admins nothing; a custody transfer leaves it untouched.
3. **Validation.** Any organization type is accepted; the only check is that the organization exists and is **active** (422 `Belongs-to organization not found.` otherwise). Deliberately no custodian-type check and no scope check. `null` clears it on PATCH; omitting the key leaves it alone.
4. **API.** `belongs_to_organization_pk` on `POST` and `PATCH` of `/properties` and `/assets`; `belongs_to_organization_pk` and `belongs_to_organization_name` in the responses; list filter `belongs_to_organization_pk`, which is ANDed with the caller's custodian-scope clause, so it never widens visibility. Audited by the generic `fn_audit_trigger()` (field-level rows in `field_change_log`) and the existing `log_audit()` UPDATE summary.
5. **Schema.** Column + FK (`fk_property_belongs_to_org`, `fk_asset_belongs_to_org`) + partial index added to `01_property.sql`/`02_asset.sql` for fresh builds, and carried to existing databases by the idempotent `database/ddl/11_assets_property/10_assets_property_belongs_to_patch.sql` (`run_sql`/`Invoke-Sql` after the 09 file). It is an additive, nullable column (SOL-AP-005 amendment note in `05_assets_property_table_design.md` §7/§8).
6. **UI.** Optional "Belongs to (if different from the holder)" picker on the create/edit form (hint: "Use this when an asset belongs to one organization (for example the Mahila Sangha) but is held under the supervision of a physical organization (for example the Kendra Sangha)."), shown in list rows and the detail header only when set, plus a list filter. The pickers reuse the scoped `/organization/organizations/in-scope` search *without* the custodian type restriction; consequence: a scoped admin can only pick organizations inside their own admin scope, while NSS-wide administrators can pick any (no unscoped organization search endpoint exists; the API itself accepts any active organization).
7. **Interaction with the AP rules.** No conflict. AP-009 (holding ≠ custody) and AP-053/054 (Mahila Sangha is competent to hold property; Mahila landed property is held in the President's name) are about the *recorded/legal holder*, which stays the free-text `holding_arrangement` of a property; "belongs to" is a third, separate fact and does not replace it. AP-049/056 (Kendra custodianship and Kutir maintenance) are untouched: a Mahila-attributed asset held by the Kendra is exactly the case this supports. No financial field is introduced (AP-060/063). No CONSTITUTIONAL rule is amended.

## 2E. Acquisition method (owner-directed, 2026-11-03; resolves open question 4)

1. **What.** A nullable `acquisition_method_master_data_pk` (FK `fk_property_acquisition_method` / `fk_asset_acquisition_method` → `nss.master_data`, partial indexes `idx_property_acquisition_method` / `idx_asset_acquisition_method`) on `nss.property` and `nss.asset`, recording HOW the record was acquired (AP-023 "when **and how**"; `acquired_at` already records when). Master-data category `ACQUISITION_METHOD`, admin-extendable through `POST /api/v1/foundation/master-data` (Master Data Driven; not a CHECK).
2. **Values.** `PURCHASE`, `DONATION` — grounded in the source documents (AP-026 and REF-003 VI(B) speak of acquisition "by purchase"; REF-001 speaks of "special donations"). `GIFT`, `BEQUEST`, `TRANSFER_IN`, `CONSTRUCTION`, `OTHER` are **candidates** not named in the source (catch-all `OTHER` included), seeded as data and removable/renamable by an admin. None is frozen in DDL.
3. **Informational only.** No effect on authorization, admin scope, the custodian rule or the lifecycle. Approval of an acquisition stays with Governance (AP-025) and any payment with Finance (AP-026); no financial field is introduced.
4. **API.** `acquisition_method_code` accepted on `POST` and `PATCH` of `/properties` and `/assets` (unknown code → 422 `Unknown ACQUISITION_METHOD value '<code>'.`; `null` clears on PATCH, omission leaves it alone); `acquisition_method_code` / `acquisition_method_name` in the responses; list filter `acquisition_method_code` (ANDed with the custodian-scope clause, so it never widens visibility). Audited by `fn_audit_trigger()` (field-level `field_change_log` rows).
5. **Schema delivery.** Column + FK + index added to `01_property.sql`/`02_asset.sql` (fresh builds) and carried to existing databases by the idempotent `11_assets_property_acquisition_method_patch.sql` (`run_sql`/`Invoke-Sql` after the `belongs_to` patch); the category and values by the existing reference-data patch. `03_validate` checks the columns, the FK orphans and the category.
6. **UI.** Optional "Acquisition method" select on the create/edit form (options from `GET /foundation/master-data?category_code=ACQUISITION_METHOD`), shown in the detail panel, plus an optional list filter. SOL-AP-005 amendment note: §7.3/§7.8 and §8.3/§8.7.

## 2F. Disposal / retirement closes the active custodianship (owner-directed, 2026-11-03; resolves open question 3)

Owner: "maybe both" — nothing stays *active* for something that is gone, yet the record still shows who last held it.

1. **Closure.** The `DISPOSED` (property) / `RETIRED` (asset) transition ENDs the ACTIVE custodianship **in the same transaction** as the status change: `status = ENDED`, `effective_to` = the transition date (never before `effective_from`), `end_reason` = the new `CUSTODIANSHIP_END_REASON` value `DISPOSED` / `RETIRED`. Both are new master-data values (existing values are not renamed); a routine custody *transfer* may not use them (422 "reserved for recording a disposal / retirement").
2. **Last custodian stays visible.** *Effective custodian* = the ACTIVE custodianship's organization, else — only for a terminal record — the organization of its most recently ENDED custodianship (latest `effective_to`, then `effective_from`, then `created_at`). One SQL definition (`api/routers/assets_property.py::_effective_custodian_join`) is used by detail, list rows, filters and every scope check. Consequence: a disposed/retired record stays visible to — and only to — the admins who could see it before; it never degrades to "custodian-less / NSS-wide only", and `custodian_organization_pk` / `include_sub_organizations` / `require_org_in_scope` keep matching it by its last custodian. A *non-terminal* record never falls back to history (a mid-life record without an active custodian is still custodian-less).
3. **Responses.** `current_custodian_*` keeps its names and now carries the effective custodian; new `custodian_is_last: bool` and `custodian_ended_at: date | null` tell the UI to show "Last custodian" and a Disposed/Retired badge. The full custody history is still returned by `/custodianships` (the ENDED row with its end reason).
4. **DB guards.** `fn_ap_entity_guard()` and `fn_custodianship_guard()` need no change for this (the custody-required rule applies only when *leaving REGISTERED*; ACTIVE → ENDED is already permitted; ENDED stays immutable). A new `nss.fn_custodianship_terminal_guard()` (`BEFORE INSERT` on `nss.custodianship`) turns the previously API-only "no further custody on a terminal record" into a DB backstop.
5. **Existing data.** The idempotent `12_assets_property_terminal_custody_patch.sql` (after the reference-data patch that seeds the two end reasons) ENDs the still-ACTIVE custodianship of records already DISPOSED/RETIRED; a no-op on fresh builds and on re-runs. `03_validate` fails if any ACTIVE custodianship remains on a terminal record.
6. **UI.** Disposal confirm text says the current custodianship will be ended today and kept in the history, with the custodian staying on the record as the last custodian; list rows and the detail header show the status badge next to the last custodian, labelled "Last custodian", plus "Custody ended".
7. **Rules check.** No CONSTITUTIONAL rule forbids this (AP-044/045 give authority to Governance; AP-046/047 and AP-LIF-003 only make the terminal states irreversible; AP-041/LIF-004 concern *transfer*, which is not a disposal; AP-072 and AP-018 are honoured — the row is ended, never overwritten or deleted). The lifecycle text (§5.3) lists no "disposal" trigger for ENDED, so this is an additive reading (SOL-AP-003 amendment note, §5.3).

## 3. Rules enforced as written

AP-001 (separate entities), AP-004..008 (UUID PKs, unique immutable ids), AP-009/012 (holding ≠ custody), AP-015/016/017/018/019 (organization-only custodian, separate temporal entity, one ACTIVE custodian via partial unique indexes, history never overwritten, property XOR asset), AP-025/045/073 (no approval here), AP-026/031/039/048/060..062 (no financial table or column), AP-029 (maintenance is a historical record), AP-034/040 (statutory records separate and property-only: no `asset_pk` column and no asset route), AP-041/042/043 (transfer ≠ state change, new custodianship, location independent), AP-046/047 (terminal states, DB-enforced), AP-058/059 (end reason; vesting preserves history), AP-067/068/069 (documents through explicit junctions to `document_master`, no local document table), AP-070/071/072 (audit columns; the generic `fn_audit_trigger()` covers all seven tables, so field changes reach `field_change_log`).

## 4. Rationale

The alternative to these choices was to stop implementation until each PENDING item had a frozen answer. Every choice above is a data row or a free-text column, so approving, amending or rejecting this record changes data, not schema (with the single exception of the CHECK "end reason required when ENDED", which follows AP-058 directly). The interpretations in §2A are the minimum needed to make the lifecycle executable.

## 5. Alternatives Considered

- **CHECK constraints for the type / end-reason / relationship values** (`SOL-AP-005` leaves "CHECK vs master" open). Rejected: freezes unapproved values in DDL; violates Master Data Driven.
- **Dedicated `property_type_master` / `asset_category_master` tables.** Rejected: §14 lists them as tables the module must not introduce.
- **A "TRANSFERRED" lifecycle state.** Rejected: contradicts AP-041.
- **Structured holder / location tables.** Rejected: AP-013/AP-022 are PENDING and §7.5/§7.6 prescribe text.
- **Leaving the ACTIVE custodianship on a DISPOSED/RETIRED record, or dropping the custodian from it.** Rejected by the owner (2026-11-03): the first leaves "active" custody on something that is gone; the second would hide who last held it and would turn the record custodian-less for authorization. The decided design ENDs the custody and keeps the last custodian visible (§2F).
- **Granting `ASSET_*` to the Advisory Board admin.** Rejected (owner-confirmed 2026-11-02): property and assets are organization-specific, and the Advisory Board is member-specific (a body of Sakha representatives), not an asset-holding organization.
