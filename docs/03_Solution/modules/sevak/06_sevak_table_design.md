# 1. Purpose

This document defines the physical PostgreSQL database design for the Sevak Sangha Module.

It translates the approved Sevak:

- Module Overview
- Lifecycle
- Participation Rules
- Business Rules
- ERD
- Sakha Session Rules
- Anchalika/Zilla Puja Rules
- Seva Rules
- UPBS Seva Rules
- Event Rules

into the database layer.

This document is the authoritative Sevak-specific physical schema reference.

---

# 2. Design Philosophy

The Sevak database follows:

```text
Person
    ↓
Membership
    ↓
Sangha Sevi
    ↓
Sevak Participation
```

The Sevak module does not duplicate authoritative Person or Membership identity.

The design follows:

```text
Database First
        ↓
API First
        ↓
UI First
```

---

# 3. Core Design Principles

The database shall follow:

* Existing Person table is reused.
* Existing Membership tables are reused.
* Existing Sangha Sevi identity is reused.
* Existing Organization/Sakha tables are reused.
* Existing Event framework is reused.
* Existing Attendance framework is reused.
* Existing RBAC is reused.
* Existing Audit framework is reused.
* Historical business records are never physically deleted.
* Configuration is preferred over hardcoding.
* Foreign keys enforce domain relationships.
* CHECK constraints enforce frozen business rules where practical.
* Unique constraints prevent duplicate business records.
* Effective-dated history is used where required.
* System-generated lifecycle changes are auditable.

# 6. `sevak_participation`

## Purpose

Represents a person's participation in Sevak Sangha.

This replaces the old conceptual `sevak_membership` table.

The term `sevak_membership` is intentionally not used because Sevak Sangha participation is **not NSS Membership**.

---

## Columns

```text
sevak_participation_pk
person_pk
sangha_sevi_pk
first_enrollment_date
current_status
current_inactivation_source
current_inactivation_reason
current_inactivation_at
created_at
created_by
updated_at
updated_by
```

---

## Primary Key

```text
sevak_participation_pk
```

Type:

```text
BIGINT
```

generated by PostgreSQL identity/sequence mechanism according to project standards.

---

## `person_pk`

Foreign key:

```text
person.person_pk
```

Purpose:

Identifies the Person participating as a Sevak.

---

## `sangha_sevi_pk`

Foreign key:

```text
sangha_sevi.sangha_sevi_pk
```

Purpose:

Links Sevak participation to the authoritative NSS Sangha Sevi identity.

NSS Membership is mandatory for Sevak participation.

---

## `first_enrollment_date`

Type:

```text
DATE
```

Purpose:

Stores the first date the person was enrolled as a Sevak.

This date is permanent.

It does not change because of:

* Transfer
* Inactivation
* Reactivation

---

## `current_status`

Allowed values:

```text
ACTIVE
INACTIVE
```

No other Sevak participation status is permitted.

Not allowed:

```text
PROBATIONARY_SEVAK
REGULAR_SEVAK
COMPLETED
WITHDRAWN
```

---

## `current_inactivation_source`

Allowed values:

```text
SYSTEM
MANUAL
```

NULL when current status is ACTIVE.

---

## `current_inactivation_reason`

Manual reasons:

```text
NO_LONGER_PARTICIPATING
PERSONAL_REASON
LONG_TERM_ABSENCE
OTHER
```

System reasons:

```text
TRANSFERRED_TO_OTHER_SAKHA
DECEASED
```

NULL when current status is ACTIVE.

---

## `current_inactivation_at`

Timestamp when the current INACTIVE state began.

NULL when current status is ACTIVE.

---

# 7. Constraints — `sevak_participation`

The database should enforce:

```text
current_status IN ('ACTIVE', 'INACTIVE')
```

and:

```text
first_enrollment_date IS NOT NULL
```

and:

```text
current_status = 'ACTIVE'
    →
current_inactivation_source IS NULL
AND
current_inactivation_reason IS NULL
AND
current_inactivation_at IS NULL
```

and:

```text
current_status = 'INACTIVE'
    →
current_inactivation_source IS NOT NULL
AND
current_inactivation_reason IS NOT NULL
AND
current_inactivation_at IS NOT NULL
```

Manual inactivation therefore cannot exist without a reason.

System-generated transfer/death inactivation records the corresponding reason automatically.

---

# 8. Person Uniqueness

A person shall not have multiple concurrent Sevak participation records representing the same continuous Sevak identity.

Recommended constraint:

```text
UNIQUE (person_pk)
```

provided the existing Person/Membership architecture confirms one person can have only one Sevak participation history.

The preferred model is:

```text
One Person
    ↓
One Sevak Participation Record
    ↓
Many lifecycle/history records
```

rather than creating a new Sevak participation record every time the person transfers or is reactivated.

---

# 9. Sangha Sevi Uniqueness

The relationship to Sangha Sevi must remain consistent with the frozen identity model.

Recommended:

```text
UNIQUE (sangha_sevi_pk)
```

where the common Membership model guarantees:

```text
One Person
    ↓
One Membership
    ↓
One Sangha Sevi ID
```

The final implementation must align with the Membership module's existing constraints.

---

# 10. Indexes — `sevak_participation`

Recommended indexes:

```text
INDEX (person_pk)

INDEX (sangha_sevi_pk)

INDEX (current_status)

INDEX (current_status, person_pk)
```

These support:

* Person lookup
* Sangha Sevi lookup
* ACTIVE/INACTIVE filtering
* Eligible participant generation

# 11. `sevak_sakha_association`

## Purpose

Stores effective-dated historical Sakha associations for a Sevak.

This is required because:

```text
First Enrollment Date
```

and:

```text
Sakha Association History
```

are separate concepts.

---

## Columns

```text
sevak_sakha_association_pk
sevak_participation_pk
organization_pk
effective_from
effective_to
association_status
source_event_type
source_event_pk
created_at
created_by
updated_at
updated_by
```

---

# 12. `organization_pk`

Foreign key:

```text
organization.organization_pk
```

The referenced organization must represent the applicable Sakha.

The Sevak module does not create a duplicate Sakha master.

---

# 13. Effective Dates

```text
effective_from
effective_to
```

represent the period during which the Sevak was associated with that Sakha.

Current record:

```text
effective_to IS NULL
```

Historical record:

```text
effective_to IS NOT NULL
```

---

# 14. Association Status

Allowed values:

```text
ACTIVE
HISTORICAL
```

The current record is normally:

```text
ACTIVE
effective_to = NULL
```

Historical records become:

```text
HISTORICAL
effective_to = populated
```

---

# 15. Source Event

The association may be created as the result of:

```text
ENROLLMENT
MEMBERSHIP_TRANSFER
REACTIVATION
OTHER_AUTHORIZED_LIFECYCLE
```

The exact source event reference is retained where supported.

---

# 16. Transfer Behavior

When Membership transfers:

```text
Sakha A
   ↓
Sakha B
```

the current association is closed:

```text
effective_to = transfer_effective_date
```

and becomes historical.

A new association is created only if the new Sakha has a Sevak Sangha.

---

# 17. No Independent Sevak Transfer

There is no Sevak-specific transfer transaction.

The authoritative trigger is:

```text
Membership Transfer
```

The Sevak module reacts to that lifecycle event.

---

# 18. No Cross-Sakha Local Participation

The database shall not create a new Sakha association merely because a member attends another Sakha's local Sevak Sangha session.

Event participation does not modify:

```text
sevak_sakha_association
```

---

# 19. Cross-Anchalika/Zilla Participation

Attendance at an Anchalika/Zilla Sevak Sangha event outside the person's own organization does not modify:

```text
organization_pk
```

in Sevak Sakha Association.

Cross-organizational attendance exists only at the Event/Participation layer.

---

# 20. Constraints — `sevak_sakha_association`

The database should prevent:

```text
effective_to < effective_from
```

and overlapping current/historical periods for the same Sevak where the project's PostgreSQL implementation permits an exclusion/range constraint.

Recommended conceptual rule:

```text
One active Sakha association per Sevak
at any point in time.
```

---

# 21. Recommended Association Indexes

```text
INDEX (sevak_participation_pk)

INDEX (organization_pk)

INDEX (effective_from)

INDEX (effective_to)

INDEX (association_status)
```

---

# 22. Current Association Rule

The current association is:

```text
association_status = ACTIVE
AND
effective_to IS NULL
```

The system must not maintain conflicting current associations.

Recommended partial unique index:

```text
UNIQUE (sevak_participation_pk)
WHERE effective_to IS NULL
```

---

# 23. `sevak_status_history`

## Purpose

Preserves every Sevak status transition.

This table provides immutable lifecycle history.

---

## Columns

```text
sevak_status_history_pk
sevak_participation_pk
from_status
to_status
change_source
change_reason
changed_at
changed_by
source_event_type
source_event_pk
remarks
```

---

# 24. Status History Values

`from_status`:

```text
ACTIVE
INACTIVE
NULL for initial enrollment
```

`to_status`:

```text
ACTIVE
INACTIVE
```

---

# 25. Status Change Source

Allowed values:

```text
SYSTEM
MANUAL
```

---

# 26. Status History Examples

Initial enrollment:

```text
from_status = NULL
to_status = ACTIVE
change_source = MANUAL
```

Manual inactivation:

```text
from_status = ACTIVE
to_status = INACTIVE
change_source = MANUAL
change_reason = LONG_TERM_ABSENCE
```

Transfer:

```text
from_status = ACTIVE
to_status = INACTIVE
change_source = SYSTEM
change_reason = TRANSFERRED_TO_OTHER_SAKHA
```

Death:

```text
from_status = ACTIVE
to_status = INACTIVE
change_source = SYSTEM
change_reason = DECEASED
```

Reactivation:

```text
from_status = INACTIVE
to_status = ACTIVE
change_source = MANUAL
change_reason = NULL
```

---

# 27. Status History Immutability

Historical status records must not be physically deleted.

Corrections must follow the centralized audit/correction process.

Normal application operations must not directly rewrite historical status records.

---

# 28. Status History Indexes

Recommended:

```text
INDEX (sevak_participation_pk)

INDEX (changed_at)

INDEX (to_status)

INDEX (change_reason)

INDEX (change_source)
```

---

# 29. `sevak_reactivation_review`

## Purpose

Represents the review cycle created when an INACTIVE Sevak attends an applicable event.

---

## Columns

```text
sevak_reactivation_review_pk
sevak_participation_pk
review_status
opened_at
opened_by
closed_at
closed_by
decision
decision_at
decision_remarks
trigger_attendance_pk
created_at
created_by
updated_at
updated_by
```

---

# 30. Review Status

Allowed values:

```text
OPEN
CLOSED
```

---

# 31. Review Decision

Allowed values:

```text
KEEP_INACTIVE
REACTIVATE
```

NULL while:

```text
review_status = OPEN
```

---

# 32. Trigger Attendance

`trigger_attendance_pk` references the common Attendance record that first triggered the review.

This provides traceability:

```text
INACTIVE SEVAK
      ↓
ATTENDANCE
      ↓
REACTIVATION REVIEW
```

---

# 33. One Open Review Rule

Only one OPEN review may exist for a Sevak.

Recommended PostgreSQL partial unique index:

```text
UNIQUE (sevak_participation_pk)
WHERE review_status = 'OPEN'
```

This directly enforces the frozen business rule.

---

# 34. Additional Attendance During Open Review

If another applicable attendance occurs while:

```text
review_status = OPEN
```

the system shall not create another review.

The attendance is associated with the existing review context through the application's lifecycle logic.

No duplicate OPEN review is permitted.

---

# 35. Review Closure

When reviewed:

```text
OPEN
  ↓
CLOSED
```

The decision must be:

```text
KEEP_INACTIVE
```

or:

```text
REACTIVATE
```

Closed reviews remain historical.

---

# 36. Reactivation

If:

```text
decision = REACTIVATE
```

the system changes:

```text
sevak_participation.current_status
```

from:

```text
INACTIVE
```

to:

```text
ACTIVE
```

and inserts:

```text
sevak_status_history
```

with:

```text
from_status = INACTIVE
to_status = ACTIVE
change_source = MANUAL
```

---

# 37. No Automatic Reactivation Trigger

The database must not contain a trigger equivalent to:

```text
ATTENDANCE
    ↓
UPDATE sevak_participation
SET current_status = 'ACTIVE'
```

Instead:

```text
ATTENDANCE
    ↓
OPEN REACTIVATION REVIEW
    ↓
AUTHORIZED DECISION
    ↓
STATUS CHANGE
```

---

# 38. Death Trigger

Death originates outside the Sevak module.

Conceptually:

```text
Person/Membership
        ↓
DECEASED
        ↓
Sevak lifecycle service
        ↓
INACTIVE
```

The system records:

```text
change_source = SYSTEM
change_reason = DECEASED
```

No Sevak approval is required.

---

# 39. Transfer Trigger

Membership transfer originates outside the Sevak module.

Conceptually:

```text
Membership Transfer
        ↓
Current Sakha changes
        ↓
Sevak lifecycle service
        ↓
Old participation INACTIVE
        ↓
New association / participation where applicable
```

All changes are audited.

---

# 40. Common Event Framework

The Sevak module shall **not create a duplicate generic activity system**.

The existing Event framework shall represent:

```text
SAKHA_SEVAK_SANGHA_SESSION
ANCHALIKA_ZILLA_SEVAK_SANGHA_PUJA
```

and future applicable Sevak events.

The old proposed:

```text
sevak_activity
sevak_activity_participant
```

tables are therefore not part of the final core Sevak schema.

---

# 41. Event Participation

Event participation belongs to the common Event framework.

Conceptually:

```text
EVENT
   │
   ▼
EVENT_PARTICIPATION
   │
   ├── PERSON
   ├── INTENTION
   └── ATTENDANCE
```

The Sevak module supplies the applicable eligibility rules.

---

# 42. Attendance

Attendance belongs to the common Attendance framework.

The Sevak module does not maintain:

```text
sevak_attendance
```

as a separate duplicate table.

The common Attendance model must support:

* Event
* Person
* Attendance status
* Attendance timestamp
* Correction
* Audit

---

# 43. Attendance Uniqueness

For each event:

```text
One Person
    ↓
Maximum One Attendance Record
```

Recommended common Attendance constraint:

```text
UNIQUE (event_pk, person_pk)
```

This is a common framework rule and should not be duplicated in the Sevak module.

---

# 44. Event Intention

Attendance intention is also part of the common Event participation model.

Possible values:

```text
WILL_ATTEND
WONT_ATTEND
NO_RESPONSE
```

Historical intention changes should be preserved where the common Event framework supports versioned responses.

---

# 45. Probable Attendance

Probable attendance is a calculated/planning view.

It should not be stored as a permanent duplicate participant table unless the common Event architecture requires a snapshot.

The system derives it from:

```text
Eligibility
+
Current Intention
+
Host Sakha Rules
+
Sevak Eligibility
```

The host can see:

```text
Probable Count
+
Individual Probable Participants
```

---

# 46. Eligibility

Eligibility is calculated from authoritative data.

For Anchalika/Zilla event:

```text
Eligible Sevaks
+
Male NSS Members
```

For Sakha event:

```text
Eligible Sevaks
+
Male NSS Members
```

Eligibility is not a new membership record.

---

# 47. Host Sakha

Every Sevak event requires a registered Sakha as host.

The Event framework stores:

```text
host_organization_pk
```

referencing the Organization/Sakha.

The host Sakha's registered location is used.

A historical location snapshot is retained by the Event framework.

The Sevak module does not create a separate venue table for this purpose.

---

# 48. Anchalika/Zilla Event Scope

An Anchalika/Zilla event stores its applicable organizational scope through the common Event framework.

Conceptually:

```text
Event
 ├── Event Type
 ├── Host Sakha
 ├── Organizing Anchalika/Zilla
 └── Location Snapshot
```

The participant's current organization remains unchanged.

---

# 49. Seva Assignment

Seva Assignment belongs to the Seva domain.

Conceptually:

```text
SEVAK PARTICIPATION
        │
        ▼
SEVA ASSIGNMENT
        │
        ▼
SEVA CATEGORY
```

The Sevak module must reference the Seva Assignment entity rather than creating:

```text
sevak_seva_assignment
```

if the common Seva module already owns the assignment.

---

# 50. Multiple Seva Assignments

One Sevak may have multiple active assignments.

The Seva schema must support:

```text
Sevak
 ├── Assignment A
 ├── Assignment B
 └── Assignment C
```

Each assignment has independent:

* Category
* Origin
* Approval
* Status
* Effective dates
* History

---

# 51. Seva Status Independence

The database must not implement:

```text
Sevak INACTIVE
    ↓
All Seva INACTIVE
```

automatically.

Instead:

```text
Sevak INACTIVE
       ↓
Active Seva Assignments flagged for review
       ↓
Each assignment independently decided
```

This rule is explicitly frozen. 

---

# 52. Training Tables

The following tables are **not part of the frozen core Sevak schema**:

```text
sevak_training_program
sevak_training_attendance
sevak_orientation_batch
```

Reason:

The current rules explicitly state that no formal training hierarchy is frozen and previously proposed training tables are not frozen. 

Training may be introduced later through a dedicated approved design.

---

# 53. Certification Tables

No Sevak certification table is frozen.

Certification/recognition remains a pending capability.

No database structure shall be created for it until business rules are approved.

---

# 54. Generic Activity Tables

The following old proposed tables are not part of the final Sevak core schema:

```text
sevak_activity
sevak_activity_participant
```

Reason:

Current event architecture separates:

```text
Sakha Sevak Sangha Session
Anchalika/Zilla Sevak Sangha Puja
Other Sevak Events
```

and uses the common Event/Attendance framework.

---

# 55. `sevak_sangha` Table Decision

The previous design proposed:

```text
sevak_sangha
```

as a separate organizational table.

The current architecture does not require this table merely to represent:

```text
Sakha has Sevak Sangha
```

because the authoritative organizational identity is already maintained by the Organization module.

Whether a Sakha has a Sevak Sangha can be represented through the appropriate Organization/Sangha capability/configuration model.

Therefore:

```text
sevak_sangha
```

is **not frozen as a mandatory physical table** in the Sevak module.

A future dedicated Sevak Sangha organizational entity may be introduced only if the Organization/Governance architecture requires it.

---

# 56. Governance Integration

Sevak governance uses the common Governance model.

Expected references:

```text
body_master
body_member_assignment
position_master
```

Provisional body type:

```text
SEVAK_SANGHA_EXECUTIVE
```

No separate Sevak-specific governance tables are frozen.

---

# 57. RBAC Integration

The Sevak module uses centralized Administration/RBAC.

No:

```text
sevak_role
sevak_permission
```

tables are created.

Authorization is evaluated using:

```text
User
+
Role
+
Organization Scope
+
Permission
```

---

# 58. Audit Integration

All lifecycle operations follow the common Audit framework.

Audit events include:

```text
SEVAK_ENROLLMENT
SEVAK_INACTIVATION
SEVAK_REACTIVATION
SEVAK_TRANSFER_TRIGGER
SEVAK_DEATH_TRIGGER
REACTIVATION_REVIEW
EVENT_PARTICIPATION
ATTENDANCE
SEVA_ASSIGNMENT
```

The exact audit table is owned by the common Audit framework.

---

# 59. Soft Delete

Core Sevak business records shall not be physically deleted.

Lifecycle state is represented by:

```text
ACTIVE
INACTIVE
HISTORICAL
CLOSED
```

as applicable.

Historical status, association and review records remain permanently available.

---

# 60. Referential Integrity

Foreign keys shall use appropriate referential actions.

Historical Sevak records should not be orphaned because a referenced Person, Membership, Organization or Event is deleted.

Because core business records are historically preserved:

```text
ON DELETE RESTRICT
```

or equivalent protected behavior is preferred for authoritative business entities.

---

# 61. Timestamp Standards

All transactional tables shall include:

```text
created_at
created_by
updated_at
updated_by
```

where required by project audit standards.

Lifecycle/history tables additionally record the effective event timestamp.

---

# 62. User References

Where:

```text
created_by
updated_by
changed_by
opened_by
closed_by
```

are stored, they reference the authoritative application user identity according to the project's Authentication/Administration schema.

---

# 63. Date and Timestamp Rules

Use:

```text
DATE
```

for:

* First enrollment date
* Effective-from date
* Effective-to date

Use:

```text
TIMESTAMPTZ
```

for:

* Status changes
* Reviews
* Audit events
* Creation/update timestamps
* Attendance timestamps

All timestamps shall follow the project-wide timezone standard.

---

# 64. Enumerations

For business values that may evolve through configuration/master data, master tables are preferred.

Fixed lifecycle values may use PostgreSQL CHECK constraints or controlled lookup values.

At minimum, the database must enforce:

```text
ACTIVE / INACTIVE
```

for Sevak status.

---

# 65. Recommended PostgreSQL Constraints

### `sevak_participation`

```text
CHECK current_status IN ('ACTIVE', 'INACTIVE')
```

### Inactivation metadata

```text
ACTIVE
→ source/reason/date NULL

INACTIVE
→ source/reason/date NOT NULL
```

### Association history

```text
effective_to IS NULL
OR
effective_to >= effective_from
```

### Reactivation review

```text
review_status IN ('OPEN', 'CLOSED')
```

and:

```text
CLOSED
→ decision NOT NULL
```

---

# 66. Recommended Partial Unique Indexes

### One current Sakha association

```text
UNIQUE (sevak_participation_pk)
WHERE effective_to IS NULL
```

### One open reactivation review

```text
UNIQUE (sevak_participation_pk)
WHERE review_status = 'OPEN'
```

These database constraints directly enforce two important lifecycle rules.

The Sevak module should not duplicate these values merely for event eligibility.

# 69. No Gender Duplication

Gender is owned by:

```text
person
```

The Sevak table must not create:

```text
sevak_participation.gender
```

unless a future approved historical snapshot requirement specifically demands it.

Current eligibility should use authoritative Person data.

---

# 70. No Current Sakha Duplication

The Sevak participation table must not maintain an independent authoritative:

```text
current_sakha_pk
```

that can diverge from Membership.

Current Sakha is derived from Membership.

Historical Sevak Sakha association is maintained separately in:

```text
sevak_sakha_association
```

---

# 71. No Membership Status Duplication

The Sevak table must not copy:

```text
membership_type
membership_status
```

as authoritative values.

These belong to Membership.

The Sevak module references Membership/Sangha Sevi.

---

# 72. No Separate Deceased Flag

The Sevak table must not create:

```text
is_deceased
```

Death is authoritative in the Person/Membership lifecycle.

Sevak reacts by becoming:

```text
INACTIVE
reason = DECEASED
source = SYSTEM
```

---

# 73. Transfer Trigger Architecture

Recommended lifecycle service flow:

```text
Membership Transfer
        │
        ▼
Membership lifecycle event
        │
        ▼
Sevak lifecycle handler
        │
        ├── Close old association
        │
        ├── Inactivate current Sevak participation
        │
        ├── Record status history
        │
        └── Evaluate new Sakha
                 │
                 ├── Has Sevak Sangha
                 │       ↓
                 │   Create new participation
                 │
                 └── No Sevak Sangha
                         ↓
                     No new participation
```

---

# 74. Death Trigger Architecture

Recommended lifecycle flow:

```text
Person/Membership marked DECEASED
        │
        ▼
Global lifecycle event
        │
        ▼
Sevak lifecycle handler
        │
        ├── ACTIVE → INACTIVE
        ├── reason = DECEASED
        ├── source = SYSTEM
        └── status history
```

The system must also ensure the deceased state is reflected consistently across other applicable participation modules.

# 75. Reactivation Architecture

```text
INACTIVE SEVAK
      │
      ▼
Applicable Event Attendance
      │
      ▼
Check existing OPEN review
      │
      ├── EXISTS
      │     ↓
      │ Attach to existing review context
      │
      └── DOES NOT EXIST
            ↓
        Create OPEN review
            │
            ▼
       Authorized Review
            │
        ┌───┴────┐
        ▼        ▼
KEEP INACTIVE  REACTIVATE
                   │
                   ▼
                 ACTIVE
```

The four tables cover the actual frozen Sevak-specific persistence requirements:

# 88. Security

```text

+

+
```

---

# 89. Database Transaction Requirements

Lifecycle changes involving multiple tables must occur within an appropriate transaction.

Example transfer:

```text
BEGIN
    Close old association
    Update participation status
    Insert status history
    Create new association where applicable
    Create new participation where applicable
COMMIT
```

If any required operation fails:

```text
ROLLBACK
```

The database must not be left with partially applied lifecycle state.

---

# 90. Death Transaction

Death-triggered Sevak update should similarly be transactional:

```text
BEGIN
    Person/Membership death state
    Sevak status update
    Status history
    Related lifecycle processing
COMMIT
```

The exact orchestration belongs to the common lifecycle service.

---

# 91. Reactivation Transaction

Reactivation should atomically:

```text
BEGIN
    Close reactivation review
    Update Sevak status
    Insert status history
COMMIT
```

This prevents:

```text
Review = CLOSED
but
Sevak = INACTIVE
```

from occurring after a successful reactivation decision.

---

# 92. Concurrency

The database must prevent:

* Two simultaneous OPEN reactivation reviews.
* Two current Sakha associations.
* Duplicate Sevak participation for the same Person.
* Duplicate attendance for the same Event + Person.

Database constraints are preferred over application-only validation.

# 94. Trigger vs Application Service

Business lifecycle orchestration should preferably be implemented in the application/domain service layer rather than putting complex business workflows into PostgreSQL triggers.

Database triggers may be used where required for:

* Audit
* Simple integrity enforcement
* Derived timestamps
* Preventing invalid state

Complex operations such as Membership Transfer → Sevak lifecycle should be handled transactionally by the application lifecycle service.

# 95. Frozen Database Rules

The following database rules are frozen:

* One Person has one Sevak participation history.
* NSS Membership is mandatory.
* Sangha Sevi ID is authoritative.
* Sevak status is ACTIVE or INACTIVE.
* First enrollment date is permanent.
* Manual inactivation requires a reason.
* Transfer inactivation is SYSTEM-generated.
* Death inactivation is SYSTEM-generated.
* INACTIVE attendance does not automatically reactivate.
* Only one OPEN reactivation review exists per Sevak.
* Historical status records are preserved.
* Sakha association is effective-dated.
* Only one current Sakha association exists.
* Cross-Sakha attendance does not alter Sakha association.
* Cross-Anchalika/Zilla event attendance does not alter organization.
* Event participation uses the common Event framework.
* Attendance uses the common Attendance framework.
* Seva Assignment is separate from Sevak status.
* Multiple Seva Assignments are permitted.
* Training tables are not frozen.
* Generic activity tables are not frozen.
* Separate Sevak governance tables are not frozen.
* Central RBAC is used.
* Central Audit is used.
* Historical business records are not physically deleted.
